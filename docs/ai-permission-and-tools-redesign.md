# AI 权限与工具层重新设计（草案 v2）

> **状态：草案，未实施。** 只回答「权限为什么不够用、tools 该怎么调、怎么分阶段迁移」，
> **不含代码改动**。
>
> 背景：AI 中间层已落地（规则、模型凭证、provider 都在服务端，见
> [`.agents/docs/ai-server-layer.md`](../.agents/docs/ai-server-layer.md)）。
>
> v2 相对 v1 的**关键修正**：v1 把「用户可自选 AI 权限」当成安全问题，那是错的 ——
> 见 §0。

---

## 0. 前提：客户端权限不是安全边界

**当前架构的两个事实**：

1. **工具执行在用户浏览器里**，用**用户自己的登录态**调后端（`execute` 走
   `getQueryClient()` / `client.*`，凭据就是用户那份）。
2. **中间层（Worker）不调任何业务接口、不代持业务身份** —— 它只做「拼提示词 + 注入模型凭证 +
   透传」，与业务后端零接触。

**由此推出的三条结论**（v1 说错的就是第 1 条）：

| # | 结论 |
|---|---|
| 1 | **客户端那份 AI 权限不构成安全边界**。用户把它改成"全部工具"，只是让 AI 去**尝试**；真正的授权发生在后端，而请求带的是**他自己的身份** —— 越权会被后端拒。 |
| 2 | 所以「让用户自己决定 AI 能用什么」是**合理的**：他在**授权自己的 AI**，风险自担，不涉及提权。 |
| 3 | 真正的问题因此不是「可篡改」，而是 **粒度太粗** 与 **三套权限并存**（下面 §2）。 |

**真边界在哪**：后端 RBAC + 用户身份。客户端这层只决定"**AI 会去尝试什么**"与
"**模型看到哪些工具**"（后者影响能力与提示词）。

> ⚠️ 这条例外的唯一情形：将来若把某个工具的执行搬到服务端（用它自己的凭证），
> 那一项就**必须**由服务端授权。现在没有这种工具。

## 1. 现状盘点（事实）

### 1.1 三套权限并存，语义、命名、判定都不同

| 层次 | 载体 | 谁决定 | 实际状态 |
|---|---|---|---|
| **AI 工具可见性** | `aiPermission`（`full`/`readonly`/`custom`）+ `aiAllowedTools` | 用户（本机偏好） | ✅ 可用，是**唯一真正在生效**的那套 |
| **业务权限点** | `user.role` + `permissions` | 后端 | **空的**：mock 只有 `role: 'Admin'`；`permissions` 传 `undefined`，而 `hasPageCapabilityPermission` 对"未接入权限清单"**默认放行** |
| **页面能力 / 指令** | `feature.ts` 的 `permissions`、`command.permission` | 同上 | 10 份 `feature.ts` 里**只有 3 份**声明（`user:create`/`user:edit`/`user:delete`） |

判定入口**已经是一处**（`hasPageCapabilityPermission`，`lib/ai/page-capabilities.ts:161`），
`resolveFeatureCommands` 也复用它 —— 这点是好设计，要保留。问题是它只覆盖后两层，
**第一层完全绕过它**。

### 1.2 16 个工具全在前端，定义与执行耦合

`lib/ai/tools/index.ts` 的 `AI_TOOLS` 是唯一真值，每个 `AiToolDefinition`：

```
name · description · inputSchema · access · group · execute
└──── 给模型看的（属于提示词）────┘        └─ 动手做的 ─┘
```

过滤只有一个入口 `getAllowedTools(permission, customTools, { hasForms, surface })`
（三条规则：权限档 → 名字集合、无表单剔 form 组、全屏剔 3 个页面工具）。

### 1.3 顺带确认：三个已知缺陷仍在

| 位置 | 问题 |
|---|---|
| `lib/ai/chat.ts:160` | 用了 `AiStreamEvent` 但**没有 import**（编译期错误） |
| `lib/ai/tools/form-tools.ts:287` | `… ?? (ctx.mode === 'ask' \|\| true)` 右侧**恒为 true** → `submit_form` 在自动模式下也强制审批 |
| `lib/ai/route-refs.ts:276` | `@` 展开文本硬编码面板策略（"必须优先 navigate_to…"）→ 违反容器中立 |

## 2. 真正的问题

### 2.1 粒度太粗：用户勾的是"工具名"，不是"业务能力"

现在设置页让用户面对 **16 个工具名**：`get_page_context` / `call_read_api` / `call_write_api` /
`fill_form` / `manage_tasks`…… **这些词对业务用户没有意义**，而且：

- **工具会增删** —— 每次加工具，用户的勾选清单都得重看一遍；
- **三档表达不了真实诉求** —— 没办法说"用户管理可以写、数据字典只读"；
- **勾了 ≠ 能用** —— 勾上 `call_write_api` 说明"允许 AI 用通用写接口"，但到底能改哪个模块的数据，
  这里看不出来。

### 2.2 三套权限并存（重复）

同一件事"能不能做某事"，被三个地方各说一遍：AI 工具勾选（工具粒度）、
`user.permissions`（权限点粒度）、`feature.ts` 的 `permissions`（页面/指令粒度）。
命名不一致（`readonly` 档 vs `user:delete` vs `command.permission`），判定入口也不统一。

### 2.3 通用写接口的权限**无法预先声明**（设计难题）

`call_write_api` 是个"什么都能打"的通道 —— 它需要什么权限，**取决于模型这一轮调的是哪个接口**，
事先声明不出来。于是它现在只能是一个粗粒度的"通用写"开关。

这条不是加个字段能解决的，§4.3 给了三个选项。

## 3. 目标模型

**一套命名，两处使用**：

| | 用在哪 | 谁算 |
|---|---|---|
| **后端 RBAC** | 真正的授权边界（带用户身份） | 后端 |
| **客户端 AI 授权** | 决定"给模型看哪些工具 / AI 会尝试什么" | 用户自己挑 |

**三条不变式**：

1. **执行层永远用用户身份**（现状即如此，不要改）。
2. **AI 授权 ≤ 用户自己的权限**（客户端负责让人挑得明白，后端负责兜底）。
3. **"要不要问"仍是独立维度**（`aiComposerMode` ask/auto + 审批卡），不要和权限混。

## 4. 方案

### 4.1 把权限收敛到「权限点」一套命名

- 权限点沿用**已有的业务命名**：`user:read` / `user:create` / `user:edit` / `user:delete` /
  `dict:write` / `feature:write` …（`feature.ts` 里已经在用这套）。
- 页面能力、页面指令、**AI 工具**三者共用同一套 —— 工具新增一个字段声明它需要什么：
  ```ts
  { name: 'run_page_command', requiredPermissions: ['user:delete'], … }
  ```
- 判定继续走**同一个入口** `hasPageCapabilityPermission`（已经是唯一实现，把 AI 工具接进去即统一）。

**收益**：去重（§2.2）—— 从此只有一套权限语言，页面、指令、工具说的是同一件事。

### 4.2 把 UI 从"工具名"换成"模块 × 能力"

用户看到的应该是他熟悉的东西：

```
用户管理    ☑ 查看   ☑ 新建   ☐ 编辑   ☐ 删除
数据字典    ☑ 查看   ☐ 修改
功能菜单    ☑ 查看   ☐ 修改
```

- **按模块分组**（来自导航清单，与 `feature.ts` 的权限点对齐），而不是 16 个工具名；
- 每组勾选的是**权限点**，由「工具声明的权限点」反推该给模型哪些工具 —— 用户不用理解工具；
- 加工具时**不动用户配置**（工具自动归到它声明的权限点下）；
- 只列**用户自己有的**权限点（AI 授权 ≤ 用户权限，§3 不变式 2）。

**缺后端时的过渡**：`permissions` 现在是空的（默认放行），所以这一版可以先用
**"导航清单能推导出的模块"**填满 UI，等后端 RBAC 接上再按真实权限收窄。

### 4.3 通用写接口（`call_write_api`）怎么办

| 选项 | 做法 | 评价 |
|---|---|---|
| **a 粗粒度开关** | 保留一个"通用写接口"权限点（`ai:write_api`），单独勾 | 最简单；但用户勾了就等于"允许 AI 改任何模块的数据"，仍然不细 |
| **b 接口 → 权限点映射** | 让后端接口清单（`GET /api`）带上权限标识，工具执行前按目标接口判 | **最细**；需要后端在接口清单里提供权限字段（现在没有） |
| **c 白名单收窄** | 只在"已授权的模块接口"集合内允许 `call_write_api`（用路径前缀匹配） | 折中：不改后端，前端用"模块 → 路径前缀"推导；漏判风险靠后端兜底 |

**建议**：先 **a**（保持现状语义，只是换个名字并入权限点体系），把 **c** 作为下一步，
**b** 记入后端需求。

### 4.4 tools 定义与执行分离 —— **价值下降，降级为可选**

v1 把这件事当成"补上服务端校验"，那一半理由在 §0 的修正下**不成立了**（没有安全缺口）。
它剩下三个真实价值：

1. **工具描述可热更新**（改完部署 Worker 即生效，不用发前端）；
2. **描述与提示词同源** —— `description` 是"给模型看的"，本质属于提示词，现在却散在客户端；
3. 前端即使被改也拿不到多余工具（**影响行为一致性，不是安全**）。

**代价**：AI SDK 在前端需要 `tools` 定义来驱动多步循环并解析 tool-call，所以前端不可能
真的"没有定义" —— 完全下沉要在协议上加一层（Worker 下发定义 → 前端构造 SDK tools）。
**结论：先不做**，等 §4.1/§4.2 落地、且有"描述要频繁热更"的真实需求时再说。

### 4.5 ✅ 已实现：权限来源 + 给模型前过滤

**① Mock 接口** `GET /permissions`（`apps/mock/server/routes/permissions.get.ts`）

返回当前用户的权限点，**细到按钮级**。`?role=` 可模拟三种角色，便于验证"权限收窄后 AI 真的拿不到那些工具"：
`super`（全量）/ `editor`（无删除权）/ `viewer`（只读）。

```json
{ "code": 0, "message": "", "result": { "role": "Super Admin",
  "permissions": ["user:read", "user:create", "user:edit", "user:delete", …] } }
```

权限点命名为 `{模块}:{动作}`（动作取 `read` / `create` / `edit` / `delete`），
**模块名与 `feature.ts` 一致** —— 页面能力、页面指令、AI 工具三处从此说同一套语言。

**② 前端在「给模型之前」过滤一次**

| 文件 | 职责 |
|---|---|
| `lib/permissions.ts` | 拉权限清单（react-query，5 分钟新鲜）；`hasPermission` 支持 `*` 通配；`ensureUserPermissions` 供 `chat.ts` 这种**非 React 环境**使用 |
| `lib/ai/tool-permission.ts` | `isToolGranted(tool, permissions)` —— 纯函数谓词（独立成文件是为了可离线验证） |
| `lib/ai/types.ts` | 工具新增 `requiredPermissions`（AND）+ `requiredPermissionsAny`（OR，支持 `*:read` 这类通配） |
| `lib/ai/tools/index.ts` | `getAllowedTools` 新增 `permissions` 选项；**不传 = 老行为**（向后兼容） |
| `lib/ai/chat.ts` | 发消息前 `ensureUserPermissions()`，与用户偏好**取交集** |

**两层权限的关系**：后端权限点 = **上限**；`aiPermission` / `aiAllowedTools`（用户偏好）= 在权限内**收紧**。
交集才是给模型的清单；硬边界仍是**执行时**用用户身份调后端。

**当前声明了权限的工具**（其余 14 个不声明 = 人人可用）：

- `call_read_api` → `requiredPermissionsAny: ['*:read']`
- `call_write_api` → `requiredPermissionsAny: ['*:create', '*:edit', '*:delete', '*:write']`
- `run_page_command` / `submit_form` 的权限在**指令 / 表单自己声明的 `permission`** 上（已有过滤），
  工具层不重复声明 —— 这也是「避免重复」的一部分。

**实测（离线，7/7 通过）**：

| 角色 | `call_read_api` | `call_write_api` | 需删除权的工具 | 纯上下文工具 |
|---|---|---|---|---|
| Super Admin | ✓ | ✓ | ✓ | ✓ |
| editor | ✓ | ✓ | ✗ | ✓ |
| viewer | ✓ | ✗ | ✗ | ✓ |
| 无任何权限 | ✗ | ✗ | ✗ | ✓ |

**⚠️ 尚未做**：

1. **契约同步**：新接口还没跑 `pnpm api`（前端暂用 `client.get({ url: '/permissions' })` 直调）；
   跑完可换成生成的 SDK 方法，接口也会进 OpenAPI。
2. **执行时按目标接口再校验**：`call_write_api` 现在只判到"有没有任一写权限"，
   更细的"这个模块能不能写"应在 `execute` 里按路径所属模块再查一次。
3. **UI（§4.2）与删掉用户自选档**：现在两者是并存的（交集），UI 仍是 16 个工具名。

## 4.6 权限点再细分：填写 / 提交 / 更新 / 删除分开

现状把"写"笼统地压在一处（`{模块}:create` / `{模块}:edit`），但**风险等级差很远**：

| 动作 | 可撤销？ | 用户能看见？ | 现在的权限点 | 细分后 |
|---|---|---|---|---|
| 查看 | — | — | `{模块}:read` | `{模块}:read` |
| 新建 | ✅ 删掉即可 | — | `{模块}:create` | `{模块}:create` |
| **AI 填写表单** | ✅ 用户盯着、没落库 | ✅ 就在屏幕上 | 无（笼统） | **`{模块}:fill`** |
| **提交表单** | ❌ 已落库 | ✅ | `{模块}:edit` | **`{模块}:submit`** |
| **数据更新**（直连接口改一条） | ⚠️ 要能改回来 | ❌ 界面不会自动同步 | `{模块}:edit` | **`{模块}:update`** |
| **删除**（含批量） | ❌ | — | `{模块}:delete` | `{模块}:delete` |

**为什么 `fill` 与 `submit` 必须分开**：填错一屏数据、用户当场能看见也能重来；提交是不可撤销的。
两者风险不同，用一个权限点表达不了"允许 AI 帮我填、但不许它替我交"。

**落点**（`feature.ts` 的声明里，页面与 AI **同源**）：

| 工具 / 动作 | 权限来源 |
|---|---|
| `fill_form` | 表单声明的 `fillPermission` |
| `submit_form` | 表单声明的 `submitPermission`（现有 `submission` 里已有 `requireApproval`，权限并进去） |
| `call_write_api`（PUT/PATCH） | `{模块}:update`（按**目标接口所属模块**判，见 §4.8 的执行时校验） |
| `call_write_api`（DELETE） | `{模块}:delete` |
| `run_page_command` | 指令自己声明的 `permission`（保持现状） |

## 4.7 敏感字段与脱敏读取

**声明位置**：跟着数据源走（`feature.ts` 的 `dataSources`），因为**只有页面知道哪块数据的哪个字段是敏感的**：

```ts
dataSources: [{
  id: 'users',
  title: '用户列表（当前页）',
  sensitiveFields: ['phone', 'email', 'idCard'],   // ← 新增
  read: () => users.map(...),
}]
```

**应用点只有一处**：`get_page_data` 在返回前统一脱敏（保留首尾、中间打码：`138****1234`）。

**两条必须分清的边界**：

1. **脱敏只作用于「AI 读取」**。页面自己显示的是原数据 —— 用户看自己的数据不需要打码。
2. **接口取数（`call_read_api`）没有页面声明可用**，它的返回结构是任意 JSON。那里只能按
   **全局敏感字段名清单**兜底（`phone` / `mobile` / `email` / `id_card` / `bank_card` …），
   作为统一出口的第二道。

## 4.8 存在性查询：`check_result_match`（**数据不出浏览器**）

**要解决的问题**：用户说"搜一下手机号 13812341234 的用户"。数据脱敏后，模型看到的是 `138****1234`
—— 它没法确认"用户说的那个号码在不在结果里"。

**做法**：不去给模型看数据，而是让它在**浏览器内存里**问一个是非题。

```
工具：check_result_match
输入：{ source?: string, field: string, value: string,
        mode: 'exact' | 'prefix' | 'contains' | 'regex' }
输出：{ exists: boolean }        ← 只有这一个字段
```

- 匹配在**前端**对**当前页面已加载的数据**做（`readFeatureData`），**不发请求、不回传任何数据**；
- 输出刻意只有 `exists` —— **不返回命中数量、不返回行内容**（每多一个字段都是多一条泄露通道）；
- 模型因此能回答"有 / 没有这个手机号的用户"，而**永远拿不到号码原文**。

### ⚠️ 但它有一个必须堵的漏洞：枚举侧信道

模型可以**逐位试探**："有 13800000001 吗？"→"…002 吗？"→ 最终**推断出真实号码**。
只返回布尔挡不住这个 —— 它挡的是"一次拿走全部"，挡不住"多次问出全部"。

**这三条防的是什么（别和后端限流混为一谈）**：

| 风险 | 防线 | 说明 |
|---|---|---|
| 接口 / 数据库被滥用、被刷 | **后端速率拦截** | 已有；而且 `check_result_match` **纯本地匹配、不发请求** —— 它这一路压根不碰后端，更不碰数据库 |
| **脱敏被逐步绕过**：值被推断 → 进对话上下文 → **下一轮随请求发给模型厂商** | **前端查询限流**（下表 a/b/c） | ← 这才是这里要补的那条 |

**两者不互相替代**：前者保护数据库，后者保护"数据不被问出去"。**"在哪算"不影响后者** ——
泄露发生在"模型知道了"那一刻，与"值由谁算出"无关。

**本地执行反而让后者更好做**：计数器放前端内存里，模型看不到、也绕不过（它只能通过工具调用去撞上限）。
最现实的触发场景甚至不是攻击 —— 用户说"把这一屏的手机号都告诉我"，模型拿不到原文（已脱敏），
自己想到用 `check_result_match` 二分，就**客观上把脱敏绕过去了**。

**三层缓解（建议全上）**：

| # | 措施 | 强度 |
|---|---|---|
| a | **探测值必须出现在用户消息里**（模型不能自造 probe 值） | **最强** —— 直接掐死枚举：用户没说过 13800000002，就不能问它 |
| b | **限流**：每轮 / 每会话最多 N 次，超出直接拒绝 | 中（抬高成本，不根治） |
| c | **审计**：记录每次 probe（字段 + 模式 + 是否命中），密集枚举可告警 | 事后 |

**a 需要一点实现**：把本轮用户原始文本传进工具上下文（`AiToolContext`），执行时检查
`value` 是否是它的子串。这会挡住"模型自己编一个号码去试"，但**不挡**用户自己贴一堆号码来试
（那是用户自己的数据，风险归他）。

**关于 `mode: 'regex'`（修正一个容易说错的判断）**：它**也只返回 1 bit**、也**只能问一个字段** ——
所以它本身并不比 `exact` "更危险"。真正的差别是**单次查询能覆盖的集合大小**：

| 模式 | 定位一个 11 位手机号需要几次 | 可行性 |
|---|---|---|
| `exact`（逐个枚举） | ~10¹¹ 次 | 不可行 |
| `regex`（二分：`^1381234[0-4]` / `[5-9]`） | **~37 次**（log₂10¹¹） | **可行** |

即：**bool 输出挡的是"一次拿走全部"，挡不住"多次问出全部"；regex 把"多次"从不可行变成可行。**

所以答案**不是禁用 regex**，而是**让限流额度小于"定位一个值所需的查询数"**：

- 每次 bool 查询泄露 **≤ 1 bit** → 每会话上限 N 次 ⇒ 总泄露 ≤ N bit；
- 11 位手机号 ≈ **37 bit** → **每会话 ≤ 20~30 次**就定位不出来（2²⁰ ≈ 100 万 « 10¹¹）；
- 这条对**大空间字段**（手机号 / 邮箱 / 身份证）成立；小空间字段（如 `status` 三选一）理论上
  一两次就能确定 —— 但那种字段**本来就不该被标成敏感字段**，所以实际不冲突。

**结论**：`regex` 可以开，前提是 **限流到位**（按上面的信息量算）+ 审计 + 探测值来自用户消息。
**限流与"收窄表达力"至少要有一样**：一时上不了限流，就先只给 `exact` / `prefix` / `contains` ——
那时枚举成本本来就不可行。

### 与现有工具的关系

- 它**替代不了** `call_read_api`：通用取数仍在（只是结果要过 §4.7 的脱敏）；
- 它是 `get_page_data` 的**搭档**：后者给"脱敏后的这一屏"，前者回答"某个具体值在不在里面"；
- 权限上它属**只读**（不改任何东西），但仍应按数据源所属模块的 `:read` 判一次。

## 4.9 所有 function tool 纳入权限卡片（含 `check_result_match`）

每个工具除了"需要什么权限点"，还要回答**"要不要逐次征得同意"**。而 `check_result_match`
**必须逐次同意** —— 它本来是只读的，但它能被用来**探测**（见 §4.8）。

**这比限流更聪明**：如果每次查询都要用户点头，那模型连续问 30 次"有没有 138xxxx…"
**用户当场就看见了**，可以直接拒绝。枚举攻击在**交互层**被挡住，而不是靠后台默默计数。

**但不能所有工具都弹卡** —— 一轮对话里模型可能调用好几次工具，逐个弹卡会把正常使用毁掉。
所以判据要挑一个**用户能理解、也说得通**的：**这次调用会不会把业务数据带进对话**。

**判据不是"工具风险等级"，而是「这次调用会不会把业务数据带进对话」**：

| 工具 | 会读数据？ | 要同意？ | 说明 |
|---|---|---|---|
| `get_page_context` / `list_navigation` / `manage_tasks` / `search_api` / `update_search_params` | ❌ 只读**元信息** | ❌ | 无隐私面 |
| **`get_page_data`**（读页面表格） | ✅ | ✅ **首次必问** | 数据会进对话上下文（哪怕已脱敏） |
| **`call_read_api`**（读接口取数） | ✅ | ✅ **首次必问** | 同上 |
| **`list_page_forms`**（读表单字段与当前值） | ✅ | ✅ **首次必问** | 表单里有用户填过的内容 |
| **`check_result_match`** | ✅（问出来的值） | ✅ **每次必问** | 它是唯一能问出**未脱敏的值**的工具（§4.8） |
| `act` / `commit`（填表 / 提交 / 写接口 / 页面指令） | — | ✅ | 现状 |

**两档同意语义**：

- **读数据 → 首次必问 + "本会话允许"**：用一个统一的会话授权键（与现有 `group:form` 同款，
  落在 `session-permissions`），用户点过之后不再打扰；**拒绝时工具抛错**（AI 改为请用户自己去看）。
- **`check_result_match` → 每次必问**：不给"本会话允许"，因为它是唯一能被用来"逐次问出原文"的工具 ——
  枚举的护栏就架在这里（§4.8）。

**机制上现成**：`AiApprovalRequest` + 三态决定（`deny` / `once` / `session`）已经支持
"允许一次 / 本会话允许"，所以弹卡不会每次都烦人 —— 用户觉得烦可以选"本会话允许"，
而**枚举场景下他不会选**（那正是我们要的）。

## 4.10 AI 不碰数据：让它写表达式，客户端来算

核心类比是 **Excel**：用户手里有表格数据，AI **不需要看数据**，只需要**写公式**；
Excel（客户端）负责求值。

```
现在：call_read_api 取 500 行 → 整包发给模型 → 模型心算
      ✗ 数据出浏览器  ✗ token 暴涨  ✗ 模型数数经常错

目标：模型写一个【表达式】→ 客户端拿本地数据求值 → 只把【结果】回给模型
      ✓ 数据不出浏览器  ✓ token 极小  ✓ 计算确定性
```

**表达式怎么表达（安全优先）**：

| 方案 | 表达力 | 风险 |
|---|---|---|
| JS 片段 + `eval` | 强 | **模型可注入任意代码** ✗ |
| JS + 白名单沙箱 | 强 | 沙箱逃逸难以保证 |
| **JSON 化操作描述**（推荐） | 中 | **完全无 `eval`** ✅ |

推荐形态（客户端只认这个结构，转成纯函数执行）：

```json
{ "op": "aggregate", "fn": "sum", "field": "amount",
  "where": [{ "field": "status", "eq": 1 }] }
```

操作集覆盖管理后台的统计需求即可：`count` / `sum` / `avg` / `min` / `max` / `groupBy` /
`sort` / `topN` / `distinct`。**永远不 eval** —— 表达式来自模型，而模型可能被页面内容操纵。

**它替代不了 `call_read_api`**：需要看原始明细时仍要取数（但结果过脱敏）；
表达式分析解决的是"**算一个数**"这类需求，而这恰好是绝大多数统计问题的形态。

## 4.11 字段注解（page 声明里最重要的东西）

**AI 要写表达式，就必须知道有哪些字段** —— 所以字段注解是 §4.10 的地基。
它同时服务**四件事**：

```ts
dataSources: [{
  id: 'users',
  title: '用户列表（当前页）',
  fields: [
    { name: 'id',         type: 'number',   label: '用户 ID' },
    { name: 'nickname',   type: 'string',   label: '昵称' },
    { name: 'status',     type: 'enum',     label: '状态',
      options: [{ value: 1, label: '正常' }, { value: 2, label: '停用' }] },
    { name: 'createtime', type: 'datetime', label: '注册时间' },
    { name: 'phone',      type: 'string',   label: '手机号', sensitive: true },
  ],
  read: () => users.map(...),
}]
```

| 字段注解服务什么 | 说明 |
|---|---|
| **AI 写表达式**（主要目的） | 知道字段名、类型、语义 —— **这就是"非常影响 AI"的地方** |
| **脱敏** | `sensitive: true` 是 §4.7 的声明源 |
| **正确计算** | `type` 决定能不能 sum、能不能按区间筛（对字符串求和是错的） |
| **枚举翻译** | `status: 1` → "正常"，模型不必猜数字含义 |

**为什么必须结构化**：现在 `shape?: string` 是自由文本，模型容易看错字段名、甚至编一个不存在的字段。
结构化之后它拿到的是一份**可校验的字段表**。

**硬约定（建议）**：

1. **字段注解必须与实际数据一致** —— `read()` 返回的行里确实要有这些字段；
2. **未注解的字段，AI 不可用**（宁缺勿猜）—— 否则它会拿 `shape` 的只言片语去猜；
3. **敏感字段仍然出现在注解里**（AI 需要知道"有 phone 这个字段，只是看不到值"），
   否则它连"该用 `check_result_match` 查 phone"都想不到。
